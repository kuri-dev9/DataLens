## 0. 서버 없이 먼저 시작하세요

실제 서버 없이 UI를 완성할 수 있습니다. 목 서버가 같은 계약으로 응답합니다.

```sh
python3 scripts/mock_server.py          # http://localhost:18121
```

설치할 패키지가 없습니다(표준 라이브러리만 사용). 데모 화면도 같이 서빙하므로
`http://localhost:18121/demo/` 를 열고 Base URL에 `http://localhost:18121`,
API key에 `dev-key`를 넣으면 바로 동작합니다.

질문 내용으로 시나리오를 고릅니다.

| 질문에 포함 | 재현되는 흐름 |
|---|---|
| (아무 말) | schema → query → dataset → 토큰 스트리밍 → `done` |
| `실패` | 도구 호출 중단 → `DL_AGENT_LIMIT` + `failed_step` |
| `기억` | `memory` 이벤트로 탐색을 건너뛰는 흐름 |

`--delay 5` 로 실제 서버의 느린 응답을 흉내 낼 수 있습니다. 실제 도구 호출 한
건은 15~20초이므로, 로딩 UI는 그 속도로 확인해 보세요.

## 1. 이 시스템이 하는 일

사용자가 한국어(또는 일본어)로 질문하면, 로컬 LLM이 그 의도를 파악해 MySQL에서
데이터를 꺼내오고 결과를 설명해 줍니다.

```
사용자: "PM_ENB_KPI_1M 테이블 어제 데이터 보여줘"
   ↓
DataLens ─ LLM(Gemma 4)이 "어떤 조회가 필요한가"를 판단
   ↓
QueryForge ─ 안전성 검증 후 SQL 생성·실행
   ↓
MySQL ─ 실제 조회
   ↓
사용자: "12,340건 조회했습니다. 주요 지표는..." + 표
```

**LLM은 SQL을 직접 쓰지 않습니다.** 구조화된 명세를 만들고, QueryForge가 그걸 검증해
SQL로 바꿉니다. 그래서 잘못된 쿼리나 위험한 쿼리가 실행될 수 없습니다.

---

## 2. 가장 중요한 것 — 채팅과 데이터는 별개 경로입니다

이 구조를 이해하지 못하면 UI 설계가 통째로 틀어집니다.

| | 채팅 | 데이터 |
|---|---|---|
| 경로 | `POST /v1/sessions/{sid}/messages` | `GET .../datasets/{did}/rows` |
| LLM | **거침** | **안 거침** |
| 응답 시간 | **7~43초** | **0.03초** |
| 내용 | 사람이 읽는 설명 + 미리보기 5행 | 전체 행 (최대 1000) |

**LLM은 데이터 전체를 보지 않습니다.** 미리보기 5행만 보고 요약 문장을 씁니다.
전체 323행이 필요하면 별도 경로로 가져와야 합니다.

왜 이렇게 만들었냐면, LLM이 한 번에 처리할 수 있는 양(약 8,000 토큰)이 정해져 있기
때문입니다. 수백 행을 밀어넣으면 앞부분이 잘려나가고 모델이 엉뚱한 답을 합니다.
그래서 **"무엇을 조회할지는 LLM이, 데이터 전달은 서버가"** 로 나눴습니다.

### 실제로 이렇게 흘러갑니다

```
1. POST /v1/sessions                    → session_id 받음
2. POST /v1/sessions/{sid}/messages     → 답변 + dataset_id (26초)
3. GET  .../datasets/{did}/rows         → 전체 행 (0.03초)
```

3번은 2번 응답에 `datasets` 배열이 있을 때만 합니다. 단순 대화면 비어 있습니다.

## 4. 성능 — 실측값과 그에 따른 판단

서버에서 직접 잰 숫자입니다. (NVIDIA A2 15GB / Gemma 4 26B / 526 테이블 DB)

| 동작 | 소요 |
|---|---|
| 세션 생성 | 즉시 |
| 카탈로그 526건 조회 | **0.058초** |
| Dataset 323행 조회 | **0.025초** |
| 채팅 — 단순 대화 | 7~43초 |
| 채팅 — 조회 1회 | 26~34초 |
| **스트리밍 첫 글자까지** | **약 19초** |
| 이후 생성 속도 | 초당 약 35토큰 (읽는 속도와 비슷) |

### 여기서 나오는 UX 판단 세 가지

**① 19초 동안 아무것도 안 나옵니다.**

스트리밍을 쓴다고 바로 글자가 나오는 게 아닙니다. LLM이 질문을 읽고 생각하는
시간(약 19초)이 먼저 있고, 그다음부터 글자가 흐릅니다. 도구 호출이 여러 번이면
첫 글자까지 2분 넘게 걸리기도 합니다. **이 시간을 메울 화면이 반드시 필요합니다.**

진행 상황은 서버가 `tool_call` 이벤트로 전부 알려줍니다. 각 이벤트에 무엇을 하려는지
(`intent`), 어떻게 됐는지(`result` 또는 `error`), 다시 시도하는지(`recovery`)가 들어 있어
그대로 한 줄씩 쌓으면 됩니다.

```
↺ 기억 참고: 과거 풀이 1건 — "PGW별 사용량 구해줄래?" (0.89)
✓ 1. 테이블 목록 → 테이블 50개 · 일부 잘림
✓ 2. PM_CEI_PGW_5M 구조 → 컬럼 90개
✗ 3. PM_CEI_PGW_5M 조회 → INVALID_TOOL_ARGUMENTS · 재시도 1/5
▸ 4. PM_CEI_PGW_5M 조회 · PGW_ID별 (2025-02-04)
```

`demo/datalens-demo.html`의 `renderTrace()`가 이 렌더링의 참조 구현입니다.

**실패해도 이 줄들은 지우지 마세요.** 어디까지 갔고 무엇이 막혔는지가 사용자에게
가장 중요한 정보입니다. 오류 응답의 `metadata.failed_step`에 중단 지점이
`{index, tool, upstream_code, intent}`로 들어 있습니다.

**② 타임아웃을 넉넉히 잡으세요.**

기본 HTTP 타임아웃(보통 30초)으로는 끊깁니다. **최소 180초, 권장 300초**로 설정하세요.
실측에서 도구 호출 9회짜리 질문이 187초 걸렸습니다. 서버는 15초마다 `: ping`
주석 줄을 보내 연결을 유지하므로, SSE 파서가 주석 줄을 건너뛰도록 해야 합니다.

**②-1 실패해도 앞서 나온 결과는 살아 있습니다.**

오류 응답에도 `datasets`와 `warnings`가 그대로 들어옵니다. 토큰이 일부라도 왔거나
표가 하나라도 그려졌다면 지우지 말고 "응답이 중단되었습니다" 표시만 덧붙이세요.

**③ 표는 기다릴 필요가 없습니다.**

`dataset` 이벤트가 오면 그 즉시 `rows`를 호출해 표를 채우세요. LLM이 아직 문장을 쓰고
있어도 상관없습니다. 사용자는 설명보다 숫자를 먼저 보고 싶어 하는 경우가 많습니다.

## 4-1. SSE 이벤트 표

`POST /v1/sessions/{sid}/messages` 에 `accept: text/event-stream` 을 주면 아래 순서로
옵니다. 모르는 이벤트 이름은 무시하세요 — 앞으로 늘어날 수 있습니다.

| 이벤트 | 시점 | 쓰는 법 |
|---|---|---|
| `start` | 항상 첫 번째 | `request_id`, `session_id` 기록 |
| `memory` | 과거 풀이를 참고할 때만 | 트레이스에 "기억 참고" 한 줄 |
| `tool_call` | 도구 호출마다 여러 번 | 진행 트레이스 (아래 참조) |
| `dataset` | 조회 결과가 생길 때 | 즉시 `rows` 호출해 표 렌더 |
| `token` | 답변 생성 중 계속 | 말풍선에 이어붙이기 |
| `done` | 정상 종료 | `metadata`로 소요 시간 표시 |
| `error` | 실패 종료 | `error.code` + `metadata.failed_step` |
| `: ping` | 15초마다 | 주석 줄. 건너뛰기 |

`done` 또는 `error` 중 **하나만** 옵니다. 둘 다 안 왔는데 스트림이 끝나면 비정상
종료이므로 "응답이 중단되었습니다"로 처리하세요.

### `tool_call` 이벤트

`status`가 세 가지입니다.

```jsonc
// 시작
{"index":3, "tool":"query", "status":"started",
 "intent":{"table":"PM_CEI_PGW_5M", "group_by":["PGW_ID"],
           "aggregations":["sum(DATA_CEI_VALUE)"],
           "partition_scope":{"kind":"time_range","column":"EVENT_TIME",
                              "from":"2025-02-04T00:00:00","to":"2025-02-04T23:59:59"}}}

// 성공
{"index":3, "tool":"query", "status":"completed", "elapsed_ms":146,
 "intent":{...}, "result":{"dataset_id":"ds_000000008", "row_count":128}}

// 실패 (같은 index로 다시 오지 않습니다. 재시도는 다음 index로 옵니다)
{"index":3, "tool":"query", "status":"rejected", "elapsed_ms":0,
 "intent":{...},
 "error":{"code":"INVALID_TOOL_ARGUMENTS", "detail":"aggregations/0: 'alias' is a required property"},
 "recovery":{"attempt":1, "budget":5, "will_retry":true}}
```

`intent`는 도구마다 키가 다릅니다. `schema`는 `action`/`table`/`name_pattern`,
`query`는 위 예시, `relationship`은 `from_table`/`to_table`입니다. **없는 키는 그냥
없습니다.** 있는 것만 골라 문장으로 만드세요.

`error.detail`은 모델용 원문이라 길 수 있습니다. 화면에는 `error.code`만 쓰고 원문은
툴팁이나 접기로 두는 편이 읽기 좋습니다.

`recovery.will_retry`가 `false`면 그 턴은 곧 `error`로 끝납니다.

## 5. 알아둘 제약

| 제약 | 값 | 영향 |
|---|---|---|
| 세션 유효기간 | 30분 | 만료 시 404. 새로 만들어 재시도해야 함 |
| 세션 저장 | 메모리 | **서버 재시작하면 전부 사라짐** |
| Dataset 보관 | 30분 / 세션당 20개 | 오래된 표는 다시 조회해야 함 |
| 한 번에 받는 행 | 기본 100 / 최대 1000 | 그 이상은 `offset`으로 페이징 |
| 채팅 미리보기 | 5행 고정 | 표는 반드시 별도 경로로 |
| 동시 요청 | 세션당 1건 | 겹치면 `DL_SESSION_BUSY` |

### 대화 이력은 서버가 보관하지 않습니다

세션이 메모리에만 있고 30분 후 사라지므로, **"어제 대화 다시 보기" 같은 기능이 필요하면
UI 쪽에서 저장해야 합니다.** 브라우저 로컬이든 별도 DB든요.

서버에 영속화를 넣을 수도 있지만 지금은 미구현입니다. 필요하면 알려주세요.

## 6. 언어 전환 (한국어 / 일본어)

세션을 만들 때 정합니다.

```json
POST /v1/sessions
{"locale": "ko"}     또는     {"locale": "ja"}
```

- 값은 **`ko` / `ja`만** 받습니다. `kr`이나 `jp`는 오류입니다
- 화면에 "한국어 / 日本語"로 보여주되 API에는 `ko`/`ja`를 보내세요
- 세션마다 독립적입니다. 같은 서버에서 두 언어가 동시에 돌아갑니다
- 언어를 바꾸려면 **새 세션을 만들어야** 합니다. 기존 세션의 언어는 못 바꿉니다
- 시간대는 항상 한국 기준입니다 (데이터가 KST로 쌓이므로)

## 7. 인증

모든 요청에 헤더 하나를 붙이면 됩니다. (`/v1/health` 제외)

```
x-api-key: <운영팀에서 발급>
```

**주의: 브라우저의 `EventSource`는 쓸 수 없습니다.** 커스텀 헤더를 못 붙이기 때문입니다.
스트리밍은 `fetch` + `ReadableStream`으로 직접 구현해야 합니다. 예제 코드는
`docs/API.md` 마지막에 있습니다.

API 키를 프론트엔드 코드에 넣지 마세요. 백엔드를 한 겹 두고 프록시하는 걸 권합니다.

## 8. 오류 처리

자주 만날 것들만 추렸습니다. 전체 목록은 AI용 문서에 있습니다.

| 코드 | 언제 | UI가 할 일 |
|---|---|---|
| `DL_SESSION_NOT_FOUND` | 세션 만료 (30분) | 새 세션 만들고 조용히 재시도 |
| `DL_UPSTREAM_TIMEOUT` | LLM이 너무 오래 걸림 | "다시 시도" 버튼. `retryable: true` |
| `DL_SESSION_BUSY` | 이전 질문 처리 중 | 입력창을 잠그거나 대기 안내 |
| `DL_DATASET_NOT_FOUND` | Dataset 만료 | "데이터가 만료되었습니다. 다시 질문해 주세요" |
| `DL_UNAUTHORIZED` | API 키 문제 | 설정 확인 안내 |

응답의 `retryable` 필드가 재시도 가능 여부를 알려줍니다. `true`면 같은 요청을 다시 보내도
됩니다.

## 9. 지금 알고 있어야 할 미완성 항목

솔직하게 적어둡니다. 오늘 첫 배포라 다듬을 게 남았습니다.

- **컬럼 조회에 필터가 없습니다.** 테이블에 컬럼이 167개인 경우도 있는데 전부 한 번에
  옵니다. UI에서 검색창을 두시는 게 좋습니다
- **답변 길이가 들쭉날쭉합니다.** 같은 질문에도 짧게 답하기도, 길게 답하기도 합니다.
  LLM 특성이고 조정 중입니다
- **응답 중 취소 기능**은 서버 쪽에 있지만(연결 끊으면 중단됨) 충분히 검증되지 않았습니다
- **대화 이력 영속화** 미구현 (5절 참조)

## 10. 결정이 필요한 것들

착수 전에 정해주시면 좋겠습니다.

1. **대화 이력을 저장할까요?** 저장한다면 UI 쪽인가요, 서버에 요청할까요
2. **표에서 정렬·필터가 필요한가요?** 지금은 서버가 주는 순서 그대로입니다.
   클라이언트에서 처리하실 건지, 서버 지원이 필요한지
3. **다운로드(CSV/Excel)가 필요한가요?** 필요하면 서버에 엔드포인트를 추가해야 합니다
4. **API 키를 프론트에서 직접 쓸지, 백엔드 프록시를 둘지**

서버는 이미 떠 있습니다. 이걸 붙여넣으면 동작합니다.

```bash
KEY=<발급받은 키>
B=<BASE_URL>          # 별도 전달받은 주소

# 1. 세션 만들기
SID=$(curl -s -X POST "$B/v1/sessions" -H "x-api-key: $KEY" \
  -H 'content-type: application/json' -d '{"locale":"ko"}' \
  | python3 -c 'import sys,json;print(json.load(sys.stdin)["session_id"])')

# 2. 테이블 목록 (즉시)
curl -s "$B/v1/sessions/$SID/catalog/tables?limit=1000" -H "x-api-key: $KEY" | head -c 500

# 3. 질문하기 (20~40초)
curl -s -X POST "$B/v1/sessions/$SID/messages" -H "x-api-key: $KEY" \
  -H 'content-type: application/json' \
  -d '{"message":"CD_CAUSE_ORIGINAL 테이블 데이터 보여줘"}'

# 4. 스트리밍으로 받기
curl -sN -X POST "$B/v1/sessions/$SID/messages" -H "x-api-key: $KEY" \
  -H 'content-type: application/json' -H 'accept: text/event-stream' \
  -d '{"message":"안녕하세요"}'
```

막히는 부분이 있으면 언제든 물어보세요.
